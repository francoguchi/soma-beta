## Why this exists

SOMA UI V2 now surfaces owner read evidence (Tasks, Spare Requests, RMAs, Fault Tags and lineage) after deliberate selections and rejects oversized/malformed responses. Nevertheless, the currently implemented detail owners use SQLite `fetchall()` without `LIMIT` for several collection queries. A browser cap of 5,000 accepted records / first 25 visible **does not constrain SQLite reads, Python materialization, JSON serialization or transport**. Nor does a UI preview of 25 events prove an owner collection has only 25 entries.

The pinned LLD-07 `bounds.json` states: “All large Inventory lists use deterministic cursor pagination with exact count queries when required by UI/preflight; rendered-page size never becomes business cardinality.” It also specifies a request allocation hard limit of 2,000, RMAs per request hard limit of 10,000, and Fault Tag memberships hard limit of 5,000. Those are **domain/safety cardinalities**, not permission to silently truncate evidence or substitute browser-visible counts.

This file **does not revise normative owner routes, authorize SQL modifications, select migration numbers, or give implementers an accepted new API**. First reconcile exact versions, completeness/freshness semantics, child query ownership, and compatibility with the pinned design.

## Compatibility and contract decisions to resolve BEFORE code

1. **V1 detail completeness and route/version evolution.** Present V1 GET detail responses include complete owner arrays; changing them in place to the first 25 without an explicit completeness marker is a correctness regression. Agree whether to introduce a distinct `DetailSummaryV2` plus separately addressable `...HistoryPageV1` child queries, or another explicitly versioned representation. Keep V1 unchanged until all its consumers and normative route declarations have an approved transition; merely creating child queries while leaving eager V1 full-array reads in hot paths does **not** solve their cost.
2. **Owner scoping and no invented membership.** A child endpoint is anchored to the *exact* Task, Spare Request, RMA or Fault Tag UUID4; no caller-supplied foreign parent, SR, spare_need or membership may override that path. A Task Inventory child query does not prove the Task exists; Task existence remains owned by LLD-05.
3. **Separate stream identity.** Each distinct nested collection uses an explicit registered query ID / sort ID, complete composite `last_key_tuple`, `filter_fingerprint` including `schema`, parent ID, stream name and every active filter, and an unambiguous null policy. Pagination for `(revision DESC,id ASC)` is not equivalent to UUID-only ascending; reverse order must be encoded and validated.
4. **Exactness, count and replay-independent reads.** Define per-stream `items`, `continuation`, `exact_total` or `has_more` semantics; compute exact totals only when UI/preflight actually requires them. Use `LIMIT page_size+1` or governed equivalent to establish `has_more`; never use empty placeholders for unevaluated query results. Prefer **25 default UI, bounded API max to be reconciled with LLD-07's up-to-500 list bounds**, not an arbitrary server cap.
5. **Concurrent updates and historical integrity.** A `ReadSnapshot` makes *one request* internally coherent, not a multi-request pagination session. Immutable append-only event streams need an agreed high-watermark / as-of token to avoid post-first-page additions altering a reading session. Mutable allocations, membership current states, obligation projections and current RMA/Fault Tag state require a verified owner revision or stronger snapshot/freshness fence; current parent revision alone may **not** cover every child join. Define what “refresh and start over” means, and prove mutation does not silently create mixed-authority pages.
6. **Cross-entity and cross-packet boundaries.** Inventory detail must not re-derive Task outcomes (LLD-05), SR lifecycle (LLD-03), Reference contact affiliation (LLD-02), or warehouse acceptance from inferred logistics. Preserve immutable submission snapshots and provenance. No read-path change authorizes mutations, SQL writes, idempotency changes or archival effects.
7. **Security and transport.** Keep `LLD12_BROWSER_QUERY_V1` authentication and request bounds, reject unknown query fields, overlong/forged/foreign/mismatched cursors and malformed UUIDs. Cursor encoding must fit actual GET limits (e.g. existing detail request max 2048 bytes) **or** its versioned replacement must have separately reviewed bounded transport capacity. Never relax global JSON, DOM, or response size limits to cover unbounded owner payloads.
8. **Migration/index authority.** Accepted migrations **0001–0019** (currently in runtime manifest) are immutable. Don't modify their bytes or select a migration number without normative allocation review. Several indexes already exist (e.g. `idx_inv_016` submission snapshots, `idx_inv_018` request lifecycle, `idx_inv_022` RMA assignments, `idx_inv_029` Task allocation events, `idx_inv_046` Fault Tag submissions), but indexing does **not** establish all required sort orders. `local_need_fulfillment_events` has a spare_need-first history index plus a task-ID FK index, not visibly a task+recorded+ID composite; Task physical consequences are indexed by `(task_id,target_device_part_unit_id,physical_consequence_id)`, not the Task query's order `(task_id,physical_consequence_id)`. Confirm candidates under actual query plans and representative fixture cardinalities; OR lineage and multi-table RMA logistics need particular attention.
9. **Non-normative examples only.** Illustrative future child routes such as `/api/v1/inventory/tasks/{task_id}/allocation-history` or `/api/v1/inventory/fault-tags/{fault_tag_id}/lineage/pages` **are not declared LLD-07 routes today**. They must never be wired into `DomainRoutes`, invoked from UI, or documented as available until design acceptance.

## Mandatory negative tests (representative)

- Forged cursor version/query/sort/fingerprint/null policy; incomplete composite tuple; cursor from another Task, RMA, Spare Request, Fault Tag or another nested collection; unexpected query parameters; percent-encoded cursor too long.
- Identical `recorded_at_utc` with distinct immutable IDs on the page boundary; same RMA in distinct membership snapshots; one parent with enough members to exceed the UI preview and backend page.
- Physical events added between page reads; mutable membership revised between reads; archive/restore or correction while browsing; no false submission, warehouse receipt, final acceptance or return closure implied.
- One parent with thousands of allocation/logistics/snapshot events and nested membership history; measured SQL work/transport size independent of total N for fixed page size, where required by accepted cost contract.
- Missing Task Inventory child vs existing Task; empty histories vs unevaluated states; exact received count vs displayed preview count; forged foreign SR/C10 evidence; no mutation API requests.

## Decisions / blockers

- **UNRESOLVED:** normative owner approval of V2 detail/child route semantics and compatibility; specific freshness and count obligations for mutable vs immutable streams; cursor-size and minimum security contracts; index/migration allocation; exact acceptance test/performance budget.
- **SAFE NOW:** keep existing read-only UI, complete focused tests, investigate query plans and current display safeguards, and continue non-mutating Objectives/Infrastructure coverage without pretending the unbounded Inventory reads are production-scalable.
- **DO NOT:** edit `src/soma/migrations/0010_inventory.sql` or any accepted migration, add the illustrative endpoints, silently cap existing V1 arrays, or expand the global response cap.

This candidate is maintained as *one review input*, not an independent source of truth. When accepted, update the pinned design authority and implementation state/traceability through the normal reconciliation workflow.
